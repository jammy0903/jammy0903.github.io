회사에서 IoT 모니터링 대시보드를 1인 운영하고 있다. 470대 정도의 아크차단기에서 올라오는 데이터가 InfluxDB 한 버킷(`arcBucket`)에 다 들어가고 있었는데, 곧 들어올 신규 하드웨어(V3) 때문에 이 구조를 갈아엎어야 했다.

이 글은 그걸 **왜 5단계로 쪼개서 했는지**에 대한 기록이다. 결론부터 말하면 한 번에 못 한다.

## 무슨 문제였나

기존 구조는 이랬다.

```
모든 게이트웨이의 MQTT 데이터  →  arcBucket  →  대시보드 쿼리 25곳
```

지금은 V1(RD 8대) + V2(IGWP x20·x70 47대), 둘 다 한 버킷. 필드 스키마가 비슷해서 어떻게든 굴러가고 있었다.

문제는 V3 하드웨어가 곧 들어온다는 것. V3는 샘플 수가 30개 → 60개로 늘고, 신규 필드(`vrms`, `active_power`, `power_factor` 등)가 추가된다. **같은 measurement에 다른 스키마를 섞으면 InfluxDB는 schema collision 에러를 낸다.**

해결책은 명확했다. 모델별로 버킷을 나눈다. 그런데 어떻게?

![멀티버킷 시스템 구축 진행 경과](/assets/img/multibucket/01_timeline.png)
*전체 작업의 진행 경과 타임라인. Phase -1(현황 진단)부터 후속 작업까지 8단계로 분해했다.*

## "한 번에 다 바꾸자"의 함정

처음엔 그냥 한 PR에 다 담아서 배포하면 될 줄 알았다.

- ModelRegistry 테이블 만들고
- BucketResolver 만들고
- 쿼리 25곳 다 고치고
- MQTT 핸들러도 라우팅 추가하고
- 백필도 같이 돌리고
- 마이그레이션도 같이 돌리고

이걸 한꺼번에 배포한다고 상상해보면 답이 나온다. **뭐 하나 터지면 어디가 원인인지 모른다.** 게다가 운영 중인 서비스라서 다운타임 윈도우가 거의 없다. 롤백을 하더라도 어디까지 되돌려야 하는지 모른다.

그래서 쪼갰다.

## 5단계로 쪼개기

### Phase 0 — 골격만 깔기 (라우팅 비활성)

ModelRegistry 테이블, BucketResolver 클래스, `GW.model_id` 컬럼만 추가한다. **호출하는 곳은 아무 데도 없다.** 그냥 정의만 해두고 배포한다.

이 단계의 의의는 "코드는 들어갔는데 동작은 안 한다"는 안전한 상태를 만드는 것이다. 뭐가 잘못돼도 사용자는 모른다. 내가 다음 Phase에서 호출하기 시작할 때부터 진짜 변화가 시작된다.

이걸 안 하고 바로 Phase 1으로 가면, 새 코드와 기존 코드가 동시에 들어가서 어디가 원인인지 분리가 안 된다.

### Phase 1 — read 경로를 단일 진입점으로 통합

기존에 InfluxDB를 조회하는 곳이 25군데였다. 각자 자기 식대로 버킷 이름을 하드코딩해서 쓰고 있었다 (`'arcBucket'`을 그냥 문자열로).

이 25곳을 전부 `_resolve_bucket(gw_id)` 함수 한 곳을 거치게 바꿨다. 함수 내부는 일단 무조건 `'arcBucket'`을 반환한다. **동작은 똑같다.** 하지만 이제 라우팅 로직을 바꾸려면 한 곳만 고치면 된다.

이건 산탄총 수술(shotgun surgery)을 미리 끝내놓는 단계다. 나중에 진짜 라우팅을 켤 때, 25곳을 동시에 수정하는 위험을 미리 제거한다.

### Phase 2 — 미등록 게이트웨이 데이터 보존

아직 등록되지 않은 게이트웨이에서 들어오는 raw payload를 별도 버킷(`unregistered_bucket`)에 따로 저장한다.

이게 왜 중요했냐면, **나중에 펌웨어가 보내는 식별 필드를 분석해야 했기 때문이다.** 이 시점엔 모델 자동감지를 어떻게 할지 몰랐다. 펌웨어팀 문서엔 모델 식별 필드가 명시돼 있지 않았다. 그냥 운영 데이터를 한 번 들여다봐야 했다.

이 Phase가 없었으면 Phase 4에서 자동감지 로직을 짤 때 분석할 데이터가 없었다.

### Phase 3 — 모델 관리 UI 신설

ModelRegistry에 row를 추가/수정하는 admin UI를 만든다. 게이트웨이에 모델을 수동으로 매핑하는 화면도 만든다.

이 시점에서 기존 운영 게이트웨이 55대에 model_id를 채워넣었다 (백필). EFPS prefix 8대는 `'rd'`로, IGWP prefix 47대는 `'x20_x70'`으로.

![백필 전후 게이트웨이 분포](/assets/img/multibucket/03_distribution.png)
*백필 전(NULL 55대)과 백필 후(rd 8대 + x20_x70 47대)의 분포. EFPS prefix는 rd, IGWP prefix는 x20_x70으로 일괄 매핑했다.*

여기서 한 가지 결정을 했다. ModelRegistry 테이블의 `bucket_name` 컬럼에 UNIQUE 제약을 두지 않기로. 처음엔 "한 모델 = 한 버킷" 1:1 매핑이라 UNIQUE를 걸었는데, 현재 운영에선 rd와 x20_x70이 둘 다 같은 `arcBucket`을 쓰고 있어서 UNIQUE가 깨졌다.

세 가지 옵션이 있었다:

1. UNIQUE 제거하고 둘 다 `arcBucket` 가리키게 둔다 (현재 구조 그대로 인정)
2. UNIQUE 유지하고 진짜로 버킷을 두 개로 분리한다 (대규모 데이터 마이그레이션 동반)
3. UNIQUE 유지하고 둘 중 하나만 새 버킷으로 옮긴다

옵션 1을 골랐다. **지금 당장 필요하지 않은 분리는 하지 않는다.** V3 들어올 때 그 모델만 새 버킷으로 보내기 시작하면 된다. 옵션 2는 멀쩡한 시스템에 위험만 추가하는 일이었다.

### Phase 4 — 쓰기 경로 라우팅 활성화 + devType 자동감지

이제 진짜 MQTT 핸들러에서 BucketResolver를 호출한다. 게이트웨이의 model_id를 보고 어느 버킷에 쓸지 결정한다.

![GW.model_id 데이터 흐름도](/assets/img/multibucket/02_dataflow.png)
*model_id가 시스템 안에서 어떻게 흐르는지. 왼쪽은 쓰기 경로(자동/수동 매핑), 오른쪽은 읽기 경로(라우팅 → UI/집계). 점선 박스는 자동 매핑 활성화 조건 3종.*

자동감지는 Phase 2에서 모아둔 unregistered_bucket의 raw payload를 직접 살펴봐서 해결했다. 펌웨어가 보내는 식별 필드는 문서에 안 적힌 `devType`이라는 키였다. EFPS 계열은 `devType` 필드 자체가 없고, IGWP 계열은 빌드 변형에 따라 `devType` 값이 20/30/32 셋 중 하나였다.

```python
def infer_modeltype(data, mqtt_id):
    if mqtt_id.startswith('EFPS'):
        return 'rd'
    if mqtt_id.startswith('IGWP'):
        dev_type = data.get('devType')
        if dev_type in (20, 30, 32):
            return 'x20_x70'
        return f'devtype_{dev_type}' if dev_type else 'unknown'
    return 'unknown'
```

이 함수 자체는 짧다. 하지만 이걸 짜기 위해 필요했던 게 Phase 0~3 전체였다.

![arcBucket 리네임 배포 시퀀스](/assets/img/multibucket/04_deploy_sequence.png)
*실제 배포 시에 단계마다 순서를 정해두고 진행했다. 다운타임 윈도우 구간을 별도로 강조해서, 어디서 사용자 영향이 발생할 수 있는지 미리 합의했다.*

## 쪼갤 때 지킨 원칙

돌이켜보니 나도 모르게 따랐던 원칙이 몇 개 있었다.

**1. 각 Phase는 독립적으로 롤백 가능해야 한다.** Phase 2를 되돌린다고 Phase 1까지 같이 되돌아갈 필요는 없다. 단계 사이의 의존성은 "Phase N+1은 Phase N에 의존한다" 한 방향이어야 한다. 양방향 의존이 생기면 그건 한 Phase로 합쳐야 한다는 신호다.

**2. "코드는 들어갔는데 동작은 안 한다"는 단계를 따로 만든다.** Phase 0이 그랬고, Phase 1도 사실상 그랬다 (`_resolve_bucket`이 무조건 `'arcBucket'` 반환). 새 코드를 일단 운영 환경에 깔아두고, 동작 변경은 별도 PR에서 한다. 코드 추가의 위험과 동작 변경의 위험을 시간적으로 분리한다.

**3. 데이터 수집을 가장 먼저 한다.** Phase 2에서 unregistered_bucket을 만든 이유다. 분석할 게 없으면 결정할 수 없다. 추측으로 코드를 짜면 나중에 다시 짜야 한다.

**4. 가장 위험한 변경(쓰기 경로)은 가장 마지막에.** Phase 4가 마지막이었다. 그 전까진 read 경로만 만지거나 추가 데이터만 모았다. **읽기는 잘못돼도 사용자가 화면 새로고침하면 끝이지만, 쓰기가 잘못되면 데이터가 영구히 잘못 들어간다.**

**5. UI는 백엔드 직후에.** Phase 3에서 모델 관리 UI를 백엔드 ORM 변경 직후에 만든 이유는, 백필 작업을 SQL로 직접 하면 실수할 위험이 컸기 때문이다. UI를 통해서 하면 폼 검증을 거치고, 변경 로그도 남는다.

## 안 좋았던 것

전부 잘 풀린 건 아니다.

**`INFLUX_ROUTING_ENABLED` env var 도입이 늦었다.** Phase 4에서 라우팅을 켜는 방식이 처음엔 코드 수정으로 직접 켜는 거였다. 운영에서 문제가 생기면 코드 롤백 → 재배포 사이클을 돌아야 했다. 뒤늦게 환경변수로 토글 가능하게 바꿨다. 처음부터 이렇게 했어야 했다. 위험한 변경은 코드 배포와 활성화를 분리한다.

**관리 UI 권한 검사 버그가 한 번 났다.** `user_has_gateway_access_safe()` 함수에 `if user_id == 'admin': return True` 라는 하드코딩이 있었는데, 내가 root 계정으로 테스트하니까 매칭이 안 돼서 403이 떴다. RBAC 시스템에 access_level 계층(Root=3, Admin=2)이 이미 정의돼 있었는데도 옛날 코드는 문자열 비교를 하고 있었다. `Permission.get_access_level(user_id, db) >= AccessLevel.ADMIN`으로 고쳤다.

이건 멀티버킷 작업과 직접 관련은 없는데, **새 기능 만들면서 기존 권한 시스템이랑 부딪치는 지점**을 발견할 수 있었다는 게 의외의 부산물이었다. 한 가지 작업에만 매몰돼 있으면 못 봤을 거다.

## 정리

쪼개야 하는 이유는 결국 **"위험을 시간적으로 분산시키기 위해서"** 인 것 같다. 한 번에 다 바꾸면 위험이 한 시점에 집중된다. 쪼개면 각 시점의 위험이 작아지고, 잘못됐을 때 어디가 원인인지도 좁혀진다.

5단계 쪼개기는 누가 시킨 것도 아니고 책에서 읽은 것도 아니다. 그냥 "이걸 한 번에 하면 망할 것 같은데" 하는 본능으로 쪼갰는데, 끝나고 보니까 이게 strangler fig pattern이라고 부르는 거랑 비슷하다는 걸 알게 됐다. 이름은 나중에 알아도 된다.

다음에 비슷한 작업을 하면 더 잘 쪼갤 수 있을 것 같다.
